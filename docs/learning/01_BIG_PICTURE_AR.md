# 1 — الصورة الكبيرة والمصطلحات

[الرئيسية](README_AR.md) · [التالي: قراءة Java](02_READING_JAVA_AR.md)

## 1.1 المشروع ده بيعمل إيه؟

تخيل موظف اختبار بيعمل الآتي: يفتح المتصفح، يدخل البرنامج، ينشئ صنفًا وعميلًا، يعمل فاتورة، يتأكد إن الصافي صح وإن الكمية نقصت من المخزن، وبعدها يمسح بيانات التجربة. المشروع بيحوّل الخطوات دي إلى تعليمات تتكرر بصورة منظمة.

لو البرنامج رجّع نتيجة مختلفة، الاختبار المفروض يقول إن فيه اختلاف ويحفظ دليلًا. الكمبيوتر ما بيفهمش كلمة «تمام» لوحده؛ إحنا لازم نحدد له: تمام يعني إيه؟ الصافي كام؟ رقم العميل إيه؟ عدد البنود كام؟

الاختبار الجيد مش مجرد إنه ضغط زر الحفظ من غير خطأ. ممكن الزر يتضغط والبرنامج يرفض، أو يحفظ عميلًا مختلفًا، أو يحفظ الكمية غلط. علشان كده المشروع بيراجع الشاشة والبيانات المحفوظة وأحيانًا الأثر على المخزون أو الرصيد.

## 1.2 مثال صغير من غير كود

**الهدف:** التأكد إن تغيير الكمية بيحفظ القيمة الصحيحة.

| الجزء | المثال |
|---|---|
| تجهيز | صنف سعره 100 وعميل ومخزن خاصين بالاختبار |
| إجراء | إضافة الصنف إلى فاتورة وجعل الكمية 1.25 |
| متوقع حسابي | قيمة البنود قبل الخصم والضريبة 125 |
| متوقع تخزين | بند الفاتورة المحفوظ كميته 1.25 |
| متوقع مخزني | أثر الكمية يتفق مع نوع المستند |
| تنظيف | إزالة المستند وبيانات التجربة وفق ترتيب الاعتماد |

الضريبة الفعلية لا نفترضها في السيناريو الطبيعي من دماغنا؛ فيه ملف يقرأ سياسة المبيعات ويستخدمها. مثال 125 هنا قيمة حسابية قبل الضريبة، مش إعلان إن كل الفواتير صافيها 125.

## 1.3 المصطلحات الأساسية

| الكلمة | معناها ببساطة | مثال هنا |

| ID | هوية السجل المميزة | itemId أو dealerId |
| DTO | شكل بيانات رجع من الخادم | خريطة قيم الفاتورة |
| Fixture | بيانات وتجهيزات يملكها الاختبار | صنف يبدأ اسمه QA-SL |
| Cleanup | تنظيف بيانات الاختبار بعده | حذف الفاتورة قبل الصنف |

## 1.4 إيه الفرق بين الأربع مجموعات؟

**Smoke:** سؤال سريع: هل الأساسيات شغالة؟ زي فحص الكهرباء والمياه قبل السكن.

**Sanity:** سؤال أوسع شوية: هل الوظائف المهمة في النطاق المعني سليمة؟ زي تجربة مفاتيح وغرف أساسية.

**E2E:** رحلة من بدايتها لنهايتها عبر أجزاء مرتبطة. زي طلب شراء يتحول لمسار شغل كامل، مش زر منعزل.

**Regression:** تغطية واسعة تحاول تكتشف إذا تغيير جديد كسر وظائف قديمة. طولها مش دليل جودة لوحده، لكنها أوسع من Smoke.

المسميات لا تضمن الاختيار تلقائيًا. في المشروع ده ملفات XML هي اللي تحدد الأسماء الفعلية. تقدر تسمي ملفًا Smoke وتحط فيه 500 حالة، لكنه كده فقد غرضه العملي.

## 1.5 النجاح معناه إيه؟

نجاح اختبار يثبت فقط إن الشروط اللي اتفحصت عدّت في التشغيل ده. نجاح Smoke لا يثبت نجاح كل E2E. نجاح الفحص المحلي لا يثبت إن API الحقيقي شغال. نجاح كل الاختبارات لا يثبت إن البرنامج بلا أي عيوب؛ ممكن فيه سلوك مفيش اختبار بيسأل عنه أصلًا.

**جملة تحفظها:** الاختبار دليل محدد، مش شهادة مطلقة.

### راجع نفسك

1. هل كود فاتورة ERP نفسه موجود هنا؟ لا؛ الموجود وصف اختبارها وأدواته.
2. هل الضغط على حفظ كفاية؟ لا؛ لازم نراجع النتيجة المقصودة.
3. ليه Fixture؟ علشان بيانات الاختبار معروفة ومملوكة وممكن تنظيفها.
4. هل 100 اختبار ناجح معناها 100 شاشة؟ لا؛ ممكن كلهم لشاشة واحدة أو نفس الدالة ببيانات مختلفة.

# 4 — رحلة اختبار حقيقي من أول الأمر لآخر التقرير

[السابق](03_ARCHITECTURE_AR.md) · [الرئيسية](README_AR.md) · [التالي](05_PAGES_AND_BOTS_AR.md)

## 4.1 زرار Run مش نقطة البداية الوحيدة

ممكن تشغّل من Maven أو من TestNG في IDE. المثال هنا Maven لأن أمره قابل للحفظ والمراجعة. Maven يقرأ `pom.xml`، يجهز المكتبات، يجمع `main` و`test`، ثم Surefire يشغل TestNG بالاختيار المطلوب.

كلمة **compile** تعني تحويل الكود لصيغة Java ينفذها. نجاحها يعني أن الأسماء والأنواع والاستدعاءات صالحة للتجميع، لا أن الفاتورة اتعملت صح. مرحلة **test** هي التنفيذ. **verify** مرحلة أبعد في دورة Maven تضم المراحل السابقة؛ في profile `ci` تستخدم قائمة الفحوص المحلية.

## 4.2 اختيار الحالة

افترض أن XML اختار `SalesInvoiceCoverageTest` والحالة `savesAndPrintsOwnedInvoice`. اسم الكلاس موجود تحت `src/test/java/Invoice`. TestNG يعرف التوارث وميثودات التجهيز. لا يقرأ وصف `@Story` ويحوله لخطوات من تلقاء نفسه؛ جسم Java هو اللي يتنفذ.

## 4.3 BaseTest يجهز المتصفح

افتح `src/test/java/Plugin_ERP/Tests/LoginTest/BaseTest.java`.

1. `setup` يقرأ الإعدادات.
2. `createDriver` يطلب متصفحًا من `WebDriverFactory`.
3. يضبط حجم النافذة والمهلة.
4. يفتح صفحة الدخول ويستدعي `LoginPage`.
5. لو التجهيز فشل، يحاول حفظ صورة وإغلاق المتصفح ثم يترك الفشل ظاهرًا.

`requirePreparedSession` يمنع السيناريو من استخدام جلسة لم تنجح في الدخول. ده مهم: لو كلمة السر غلط، ما ينفعش نملأ التقرير بمئة فشل «زر حفظ مش موجود» كأنها مئة عيب مستقل.

المتصفح هنا لكل كلاس في المسار المعتاد، وليس بالضرورة متصفحًا جديدًا لكل ميثود. فيه تجهيز لكل حالة داخل نفس الكلاس. لذلك ما نغيّرش طريقة التشغيل لتوازي الحالات من غير إعادة تصميم الملكية.

## 4.4 السيناريو يحدد نوع المستند

`SalesScenarioTest.kind()` يحدد فاتورة أو عرض سعر أو أمر أو مرتجع. `SalesDocumentKind` يربط نوع المستند بمساره ونوعه وendpoint. `beginSalesScenario` يجهز كائن الصفحة المناسب، علامة ملكية، وبيانات الحالة.

العلامة مثل `QA-SL-...` مش مجرد اسم لطيف. بنستخدمها للربط بين ما الاختبار عمله وما بيراجعه أو بينظفه. لا تعتمد على عبارة «آخر فاتورة» لو اختبارات أو أشخاص آخرون ممكن يعملوا فواتير.

## 4.5 البيانات قبل الشاشة

في `prepare` يتم الحصول على صنف وعميل ومندوب ومخزن، وقراءة خصائص العميل والتأكد أنها تسمح بنوع العملية. بعد كده تتفتح شاشة المستند ويُنتظر الفورم، ثم تتحدد المراجع المطلوبة.

في بعض القوائم، البرنامج يحمل الخيارات عند فتح الشاشة فقط. إنشاء الحساب بعد التحميل ممكن يخليه موجودًا بالخادم وغائبًا عن القائمة. ده حصل في اختبارات المصروفات والإيرادات وتعريف المخزن، واتصلح ترتيب التجهيز بإنشاء الحساب قبل التنقل. دي قاعدة عملية مهمة: **بيانات موجودة في API لا تعني أن كل شاشة قديمة عندها أحدث نسخة منها**.

## 4.6 الصفحة تنفذ والمكون يتخصص

`page.slQuantity(item.name(), "2")` تصل إلى واجهة صفحة المبيعات، ثم `SalesDocumentLines` يتعامل مع سطر الصنف. `slAddPicker` يصل لمكون اختيار الصنف. `slSave` يصل لفورم المستند. أسماء الدوال مش خطوات باللغة الطبيعية؛ هي واجهات نادتها دوال السيناريو.

الانتظار جزء من العملية: ممكن الفورم يظهر قبل تحميل بياناته. لو كتبنا مبكرًا، استجابة الخادم قد تستبدل ما كتبناه. لذلك دوال مثل `slFormReady` و`slWaitNet` تحاول انتظار حالة لها معنى.

## 4.7 الحفظ: أربع طبقات مختلفة

| الطبقة | السؤال |
|---|---|
| واجهة | هل زر الحفظ اتضغط وهل ظهر خطأ؟ |
| مراقبة الطلب | هل المستند المملوك دخل في محاولة حفظ؟ |
| تخزين | هل نقرأ المستند المحفوظ بهويته ونجد القيم المطلوبة؟ |
| أثر العمل | هل تغير المخزون أو الرصيد بما يناسب نوع العملية؟ |

`SalesSaveCapture` يراقب طلبات تخص علامة الاختبار وعناصره. المراقبة تعتمد على تطبيق Vue وstore داخله؛ ليست خدمة خلفية مستقلة ولا بديلًا عن حفظ UI في الحالة التي تقيس UI. إنشاء fixtures عبر API قبل السيناريو شيء مختلف عن تنفيذ عملية الحفظ الرئيسية عبر الشاشة.

## 4.8 الطباعة

حالة الطباعة تفتح نافذة أو تبويبًا إضافيًا. لازم نعرف التبويب الرئيسي، نستنى الجديد، نقرأ المحتوى، ونتأكد من البنود والأرقام المتوقعة، ثم نغلق الإضافي ونرجع للرئيسي. فصل ده في `SalesPrintWindows` أو `PurchasePrintWindows` يمنع تكرار منطق النوافذ في كل اختبار.

وجود طباعة المستند ضمن التحقق لا يعني إن كل شاشة التقارير المستقلة اتغطت. دي حدود مختلفة في المشروع.

## 4.9 التنظيف لا يسقط لأن التحقق فشل

بعد الحالة تُجمع محاولات الحفظ، وتُسجل الكيانات التي نتجت، ويحاول مالك البيانات تنظيفها. لو رد الحفظ ضاع، الخادم قد يكون حفظ بالفعل؛ ملف المحاولات يساعد على اكتشاف ذلك قبل حذف المراجع.

قائمة `pending` في سيناريوهات معينة تتيح إعادة محاولة تنظيف النطاقات التي لم تُغلق. التفاصيل تختلف حسب المجال؛ ما تفترضش إن كل السيناريوهات بتستخدم نفس كلاس التنظيف.

## 4.10 التقرير

`TestNGListeners` يجهز بيانات التقرير، يلتقط صورًا عند نتائج الحالات، ويعمل مهام التقرير عند النهاية وفق السياسة والإعداد. فشل إرسال التقرير مش مساويًا لفشل الفاتورة. والعكس: نجاح SMTP مش نجاح اختبار. التقرير له طبقة تشغيل منفصلة.

### تدريب تتبع فعلي

افتح بالترتيب: XML → `SalesInvoiceCoverageTest.savesAndPrintsOwnedInvoice` → `SalesScenarioTest.prepare` → `SalesModulePage.slQuantity` → `SalesDocumentLines.slQuantity` → `SalesScenarioTest.save` → `SalesTestData`.

اكتب بجوار كل انتقال «ليه انتقلنا؟». لو قدرت تشرح الرحلة دي لشخص تاني، أنت فهمت قلب المشروع.

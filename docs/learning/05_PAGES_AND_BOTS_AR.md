# 5 — الصفحات والمكونات وBots

[السابق](04_TEST_JOURNEY_AR.md) · [الرئيسية](README_AR.md) · [التالي](06_DATA_AND_CLEANUP_AR.md)

## 5.1 ثلاث أسئلة تحدد مكان الكود

**عايز أتأكد من إيه؟** مكانه في الاختبار أو سيناريو العمل.

**هعمله على الشاشة إزاي؟** مكانه في Page Object ومكوناته.

**إزاي أضغط أو أكتب أو أختار بشكل متكرر؟** مكانه في أدوات التفاعل.

مثال: «الصنف المحذوف من الفاتورة لا يتحفظ» توقع في الاختبار. «اضغط أيقونة حذف بند اسمه كذا» وظيفة مكون البنود. «انتظر العنصر قابلًا للضغط واضغطه» أداة تفاعل. الثلاثة مرتبطون لكن ليسوا نفس المسؤولية.

## 5.2 Locator يعني عنوان عنصر

```java
By.cssSelector("input[name='arabicName']")
```

معناه دور على input اسمه `arabicName`. `By.xpath` أسلوب آخر للبحث بالعلاقات والنصوص. `By.id` بحث بمعرف. المعرف وحده لا يضمن ظهور العنصر؛ قد يوجد عنصر مخفي بنفس الغرض.

الـlocator مش هو العنصر. `By` وصف قابل لإعادة البحث، و`WebElement` نتيجة بحث في لحظة. لما Vue يعيد رسم الجدول، العنصر القديم قد يصبح **Stale**: مرجع لشيء انتهى، حتى لو شايف صفًا شبيهًا على الشاشة.

## 5.3 الانتظار الجيد

تخيل سألت موظف «خلصت؟» كل نصف ثانية لحد عشر ثوانٍ. ده explicit wait. مش انتظار عشر ثوانٍ دائمًا؛ لو الشرط تحقق في الثانية الأولى، يكمل.

`Thread.sleep(5000)` مختلف: توقف ثابت خمس ثوانٍ، حتى لو الصفحة جاهزة، وقد لا يكفي لو الخادم أبطأ. عشان كده الانتظار على «الصف اتحدث» أو «الصافي بقى المطلوب» أفضل من تأخير عشوائي.

`WaitManagement` يبني انتظارًا بإعداد عام وبعض الاستثناءات التي يعيد المحاولة عندها. `WaitActions` فيه دوال انتظار أعلى مثل جاهزية التقرير. ومكونات القوائم لها انتظار خاص، مثل `GridProviderWait` الذي يتحقق من حالة بيانات الجدول بدل الاكتفاء بظهور مربع البحث.

## 5.4 خريطة مكونات المبيعات

| المكون | يفهم إيه؟ | ما نحطش فيه إيه؟ |
|---|---|---|
| SalesDocumentForm | حقول وحفظ وتنبيهات وجاهزية المستند | إنشاء عميل fixture |
| SalesDocumentLines | بنود وكميات وأسعار وإجماليات شاشة | اختيار مجموعة Smoke |
| SalesItemSelection | بحث الصنف وباركود ونافذة أصناف | حساب السياسة الضريبية المستقلة |
| SalesChoiceControls | اختيار ومسح قيم القوائم | تنظيف بيانات بعد الرن |
| SalesDocumentList | نطاق القائمة وفلاترها وقراءات مرتبطة بها | إدارة كلمة السر |
| SalesSaveCapture | محاولة الحفظ ونتيجته للمستند المملوك | اختيار نتيجة نجاح بدل التوقع |
| SalesPrintWindows | تبويبات الطباعة والتحقق عبر الصفحة | تعريف نسب ضرائب ثابتة |

للمشتريات مكونات مماثلة بأسماء Purchase، مع اختلاف selectors وتفاصيل المجال. التشابه لا يبرر دمج كل شيء إذا اختلف سلوك الفعل نفسه.

## 5.5 قائمة الفواتير نموذج ممتاز للمذاكرة

`InvoicListPage` ينسق `InvoiceListFilters` و`InvoiceListGrid` و`InvoiceListCalendar` و`InvoiceListPagination` و`InvoiceListExport`. خذ مثال «ابحث بالكود ومن تاريخ»: الفلاتر تضبط القيمة، التقويم يختار التاريخ، انتظار الجدول ينتظر النتيجة، والاختبار يراجع أن الكود المعروض هو المطلوب.

الاستدعاء العام القديم بقي متاحًا غالبًا، بينما التنفيذ تحرك. ده اسمه واجهة توافق. ليس لازم الاختبار يعرف أن كل دالة اتحركت لمكون جديد.

## 5.6 Bots بالتفصيل

| الملف | وظيفته الحالية | تقييم القراءة والصيانة |
|---|---|---|
| BaseAction | اعتمادات مشتركة ومساعدات scroll وJS click | قاعدة أدوات، ليست صفحة |
| ElementActions | ينشئ أدواته ويقدم getters وضغطًا وكتابة وعمليات صفوف | واجهة قديمة واسعة وتحتاج تنظيمًا لاحقًا |
| DropdownActions | التعامل مع قوائم Vue واختيار المنتجات | فيه retries وانتظارات ونصوص مرتبطة بالتطبيق |
| CheckboxActions | طرق مختلفة لضبط وقراءة Checkbox | تعدد الطرق يستلزم اختيار المناسب وعدم الدمج العشوائي |
| GridActions | قراءة الجداول وتعديلها وحذف سجلات | خلط القراءة والحذف العام مهم عند الصيانة |
| WaitActions | انتظار عناصر وروابط وتقارير وحالات شاشة | يجمع انتظارًا عامًا وآخر متخصصًا |
| WaitManagement | إعداد fluent wait | بسيط لكن اسم الإعداد `defultwait` تاريخي |
| BrowserAction | تنقل وتبويبات وإعادة محاولة | بعض الوظائف تعتمد على بيئة التشغيل |
| ValidationActions | قراءة وتطبيع ومطابقة نصوص وأرقام وتواريخ | يربط قراءة DOM بتفسيره |
| PriceListActions | خطوات خاصة بقوائم أسعار | مجال خاص داخل فولدر أدوات عامة |
| UtilityActions | تواريخ وتشخيص ومساعدات متنوعة | اسم عام؛ راجع الميثود نفسها قبل الاستخدام |
| AlertAction | تنبيهات ورسائل تأكيد | فرّق بين browser alert وSwal داخل DOM |
| LogUtils | كتابة رسائل السجل | لا تجعل الرسالة وحدها assertion |
| InvoiceValidation | ملف فارغ حاليًا | لا تتوقع منه تحققًا نشطًا |

التقييم ده لا يعني أن كل دالة معطلة. فيه أجزاء مستخدمة وناجحة، لكن الطبقة تحتاج مراجعة مستقلة لو هنحسن موثوقيتها. آخر فصل Page Objects لم يكن إعادة كتابة لكل Bots.

## 5.7 FormInteractions وNativeCheckbox

`Util/FormInteractions` يجمع سياسات كتابة واختيار وضغط تستخدمها صفحات أحدث. سياسات مثل `EXACT` و`EXACT_THEN_CONTAINS` مش متكافئة: الأولى تريد النص نفسه، والثانية تسمح باحتواء وفق آلية معينة. اختيار سياسة أوسع قد يختار صنفًا شبيهًا غلط، لذلك توجد اختبارات محلية لسياسة الاختيار.

`NativeCheckbox` يعالج ضبط Checkbox عبر التفاعل المناسب. قبل إضافة مساعد جديد، شوف هل فيه قدرة جاهزة هنا أو في Bots. ثلاثة تطبيقات مختلفة لنفس العملية يزيدوا فرصة اختلاف السلوك.

## 5.8 JavaScript داخل Selenium

فيه قراءة لحالة Vue وstore، وفيه سكربتات scroll أو أحداث input. وجود JS لا يعني تلقائيًا إن الاختبار سيئ، لكن لازم تعرف دوره. قراءة هوية مستند محفوظ تختلف عن كتابة بيانات داخل component لتجاوز الشاشة.

عند المراجعة اسأل: هل السكربت يلاحظ ما فعله المستخدم؟ أم ينفذ إجراء كان المفروض UI يختبره؟ الدليل لا يساوي بين الاثنين. لا تغير حالة التطبيق مباشرة لتجعل اختبار UI ينجح.

## 5.9 أين تضع مشكلة جديدة؟

لو barcode المبيعات لا يضيف صنفًا، ابدأ من اختبار الحالة، ثم `SalesItemSelection` والردود والأدلة، مش من تعديل كل أدوات الكتابة. لو كل الشاشات فشل فيها الضغط بعد تحديث Selenium، وقتها راجع الأدوات العامة والمتصفح. تحديد النطاق يقلل التغييرات غير الضرورية.

# 6 — بيانات الاختبار والتنظيف والاسترجاع

[السابق](05_PAGES_AND_BOTS_AR.md) · [الرئيسية](README_AR.md) · [التالي](07_CALCULATIONS_AND_ASSERTIONS_AR.md)

## 6.1 ليه ما نستخدمش أي عميل موجود؟

لأن العميل قد يتغير أو يتوقف أو لا يسمح بعملية معينة، وقد يكون له رصيد حقيقي. الاختبار ساعتها لا يعرف نقطة البداية، ولا يعرف إذا حذف أو عدّل بيانات تخص شخصًا آخر.

المشروع يستخدم بيانات مملوكة: أسماء بعلامات فريدة، IDs مسجلة، ومراجع معروفة. «مملوكة» معناها الاختبار أنشأها وسجل هويتها، مش إنه كل اسم يبدأ QA مسموح حذفه.

## 6.2 خريطة تجهيز البيانات

| النوع | مثال | دوره |
|---|---|---|
| المالك | SalesTestData | يسجل ما أنشأناه ويتابع القراءة والتنظيف |
| وصف البيانات | SalesFixtureDefinitions | يحدد حقول العميل والصنف والحسابات |
| النقل | SalesFixtureApi | ينفذ الطلب عبر جلسة ERP الحالية |
| البديل المحلي | SalesFixtureApiStub | يحاكي النجاح والفشل في اختبارات التنظيف |
| الاسترجاع | SalesFixtureRecovery | يساعد على متابعة نطاق قديم توقف |
| قواعد مشتركة | FixtureSession | يتأكد من نفس العنوان والفرع |
| سجل قبل الطلب | PendingFixtureWrites | يسجل نية الإنشاء قبل ضياع الرد المحتمل |
| كتابة السجل | FixtureJournals | تنظيم حفظ سجلات التجربة |

يوجد نفس النمط مع اختلاف التفاصيل في المشتريات والمنتجات والمخازن والحركات المالية والمتعاملين والمبيعات الخاصة. البيانات الأساسية تستخدم `BasicDataFixtures`.

## 6.3 الإنشاء والحفظ الرئيسي شيئان مختلفان

إنشاء صنف عبر API لتجهيز اختبار فاتورة لا يجعل الاختبار «API فقط». العملية المستهدفة قد تظل إضافة الفاتورة عبر UI وقراءة نتيجتها من API. ده يقلل وقت التجهيز ويجعل كل حالة تركز على هدفها.

لكن لا ينفع نستبدل حفظ الفاتورة المستهدف بـAPI ثم نقول UI الحفظ نجح. لازم توضح لكل حالة: أي جزء تجهيز وأي جزء هو العمل المقاس؟

## 6.4 dependencies بين البيانات

فاتورة تحتاج عميلًا وصنفًا ومخزنًا. الصنف قد يحتاج وحدة وتصنيفًا. العميل قد يحتاج حسابًا. لما نمسح، نعكس الاعتماد: المستند أولًا ثم الكيانات التابعة، ثم المراجع المشتركة إذا لم يعد شيء يحتاجها.

```mermaid
flowchart LR
    A[حساب أو وحدة أو تصنيف] --> B[عميل أو صنف]
    B --> C[فاتورة]
    C --> D[مرتجع أو تخصيص أو مستند مرتبط]
```

ده مثال تعليمي للاعتماد، والترتيب الحقيقي يعتمد على المجال والمستندات الموجودة. في الرحلات المركبة يستخدم `WorkflowCleanupOrder` معلومات الكيانات والعلاقات لتنظيم التنظيف.

## 6.5 مشكلة رد الطلب الضائع

الاختبار يرسل إنشاء فاتورة. الخادم يحفظها. الشبكة تقطع قبل وصول ID. لو اعتبرنا «لم يصل رد» معناها «لم يحدث حفظ»، قد نترك فاتورة يتيمة أو نحذف مراجعها خطأ.

`PendingFixtureWrites.start` يسجل الطلب قبل إرساله. بعد التأكد من الالتزام يسجل `committed`. لو الرد ضاع، الاسترجاع يبحث عن السجل المملوك بدقة وفق الهوية والعلامة والحقول المتوقعة. لو أكثر من نتيجة محتملة، الوقوف أفضل من تخمين أي سجل نمسح.

## 6.6 حارس البيئة والفرع

`FixtureSession` يحفظ `origin` و`branchId`، ويعيد التحقق قبل التعامل. `origin` عنوان خدمة الويب في الجلسة. الفرع يحدد سياق البيانات. سجل استرجاع لبيئة مختلفة لا يصح تطبيقه على بيئتك الحالية لمجرد تشابه IDs أو أسماء.

هتلاقي رسالة مثل «ERP origin or branch changed; refusing fixture access». دي حماية ملكية، مش bug لازم نشيله عشان الرن يكمل.

## 6.7 target مش مجرد مخلفات

فيه ملفات تجميع يمكن إعادة بنائها، لكن فيه كمان سجلات بيانات غير مكتمل تنظيفها. عشان كده **لا تشغّل `mvn clean` ولا تمسح target بشكل عام بعد رن حي متوقف قبل مراجعة السجلات**. إعادة البناء شيء، واسترجاع IDs بيانات على الخادم شيء آخر.

ملف journal فارغ `[]` في نطاق معين علامة أن هذا السجل لم يعد يحتوي عناصر معلقة، لكنه لا يثبت خلو قاعدة البيانات كلها من كل تجارب التاريخ. اقرأ نتيجة cleanup وملفات attempts معاه.

## 6.8 هل كل البيانات تتمسح دائمًا؟

التصميم يحاول تنظيف بياناته، لكنه قد يرفض أو يفشل لو البيئة تغيرت أو API رفض الحذف أو فيه ارتباط لم يُحل. وبعض سيناريوهات التدقيق مثل تاريخ تسليم خزينة مغلق ومراجع قد تحفظ بيانات المراجعة عمدًا. `preserveAuditHistory` موجود لهذا الغرض؛ ما تعتبرش كل سجل باقٍ خطأ بدون فهم الحالة.

وجود `DeleteAll` في أداة قديمة لا يعني أنها طريقة التنظيف المناسبة. التنظيف الحديث مبني على ملكية البيانات، وليس حذف كل ما يظهر في الجدول.

## 6.9 إزاي نتأكد أن التنظيف نفسه صحيح؟

اختبارات مثل `SalesCleanupTest` و`PurchaseCleanupTest` تحاكي مواقف: حذف فشل، استجابة ضاعت، سجل غريب، فرع تغير، اعتماد يمنع حذف مرجع. لازم هذه الفحوص تكون محلية ومضبوطة؛ مش نجرب كل سيناريو كارثي على بيانات أشخاص حقيقيين.

الفحوص دي جزء من سبب وجود مئات استدعاءات CI رغم أنه لا يعمل عملية ERP حية. نحن نختبر ذكاء الأداة في إدارة البيانات، مش فقط أسعار فواتير.

## 6.10 موقف عملي

فشلت حالة بعد حفظ مستند، والمتصفح اتقفل. الخطوات الصحيحة: احتفظ بالنتائج والسجلات، اعرف البيئة والفرع وmarker، اقرأ فشل التنظيف، استخدم مسار الاسترجاع المناسب بعد مراجعة نطاقه، ثم تحقق أن المستندات التابعة اتعالجت.

الخطوات الخاطئة: امسح target، أعد الرن عشوائيًا عشر مرات، ثم احذف كل أسماء QA من البرنامج. ده يفقد دليل المشكلة وقد يؤذي تشغيلًا آخر.

## ليه كثرة بيانات الاختبار ممكن توقف Sanity؟

بيئة Demo لها حد لعدد المخازن. لو بيانات اختبارات قديمة فضلت موجودة، إنشاء مخزن جديد قد يرجع `License Limitation Exceeded` قبل الوصول للشاشة المراد اختبارها. ده فشل تجهيز بيانات، وليس دليلًا على تعطل كل الشاشات التي ظهرت حمراء. نراجع سجلات الملكية ثم نسترجع تنظيف السجلات القابلة للحذف. أسماء QA وحدها لا تكفي لاتخاذ قرار حذف.

الجرد المقفول استثناء مقصود: مستنداته ومراجعه محفوظة كسجل حركة، فلا نحذفها لفتح مساحة. اختبار التسوية يستخدم `inventoryItem` الذي يجهز مخزنًا واحدًا بدل مخزنين؛ عمليات التحويل وباقي الاختبارات التي تحتاج مخزنين تحتفظ بوصفة `item` المعتادة. تقليل الاستهلاك لا يلغي نمو تاريخ الجرد مع التكرار؛ راقب سعة بيئة الاختبار وخطط لإدارة تاريخها وفق قواعد البرنامج.

## الصلاحيات جزء من تجهيز البيانات

إنشاء مستخدم وخزينة ومحضر فتح لا يكفي وحده لسيناريو دفتر الخزينة. في هذه النسخة، صلاحية `viewSafes` تتيح الاطلاع على الخزن، لكن استجابة شاشة سند القبض لا تعيد `UserSafes` للمستخدم المحدود بدون `viewSafeTransactions`. المقارنة الحية بمستخدمين مملوكين للاختبار أكدت ذلك. عالجنا وصف مستخدم سيناريو الخزينة بإضافة الصلاحية المطلوبة، مع بقاء المستخدم محدودًا. إذا كان العنصر لا يظهر، راجع البيانات والصلاحيات قبل تغيير محدد العنصر أو زيادة الانتظار.

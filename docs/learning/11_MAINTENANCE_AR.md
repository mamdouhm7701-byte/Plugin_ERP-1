# 11 — إضافة اختبار وصيانة المشروع

[السابق](10_MODULES_AR.md) · [الرئيسية](README_AR.md) · [التالي](12_STUDY_AND_FAQ_AR.md)

## 11.1 قبل كتابة أي سطر

اكتب جملة هدف: «عند إزالة بند قبل الحفظ، لا يظهر البند في المستند المحفوظ ولا يؤثر على المخزون». حدد المتوقع، ونوع المستند، والبيئة، والبيانات المطلوبة، ومن يملكها، والتنظيف. لو مش قادر تكتب المتوقع، كتابة Selenium لن تحل الغموض.

## 11.2 اختار مكان التغيير

| نوع التغيير | المكان المناسب عادة |
|---|---|
| زر أو حقل تغير مكانه في شاشة واحدة | مكون الصفحة المعني |
| حساب ضريبة أو تقريب مستقل | Calculator مع فحص محلي |
| مرجع جديد مطلوب لكل حالة في مجال | FixtureDefinitions ومالك البيانات |
| رحلة شراء ثم تصنيع ثم بيع | Workflow واختبار EndToEnd |
| قاعدة تشغيل أي حالات في Smoke | XML وفحوص عقود SuiteSupport |
| فشل اختيار عام في عدة صفحات | أداة التفاعل بعد جمع دليل من الشاشات |
| سياسة تقرير أو إرسال مرفق | Utiel/Allur واختباراته المحلية |

لا تكتب طلب API داخل مكون بنود عشان يسهل عليك التجهيز، ولا تضع بيانات عميل حقيقية ثابتة في Page Object. وضوح الطبقة يحميك من ربط سلوك الشاشة بتجربة واحدة.

## 11.3 خطوات إضافة حالة على مجال موجود

1. اقرأ Scenario الخاص بالمجال ودوال التحضير والحفظ.
2. حدد هل فيه Page method أو component جاهز يؤدي الإجراء.
3. أنشئ البيانات عبر مالك fixtures الموجود، وسجل أي كيان جديد بنفس آليته.
4. أضف حالة اسمها يوضح الهدف، ووصفًا يفهمه قارئ التقرير.
5. نفذ الإجراء في UI إذا هو موضع الاختبار، ثم راجع القيمة المحفوظة والأثر المناسب.
6. تأكد أن الفشل لا يمنع تجميع المستندات والتنظيف.
7. اختر مستوى التشغيل المناسب، وأعد فحص XML ثم الحالة المتأثرة.

مثال تعليمي مختصر، لا ينسخ ككلاس كامل لأنه يحتاج سياق السيناريو:

```java
prepare("Credit");
add(item, "picker");
page.slQuantity(item.name(), "1.25");
page.slWaitNet(salesNet("125"));
var saved = save(false);
sameNumber(firstLine(data.read(saved)).get("quantity"), "1.25");
assertStock("1.25");
```

الأسطر دي مفهومة داخل `SalesFormActions` حيث الحقول والدوال الموروثة موجودة. نسخها في ملف عشوائي سيؤدي لأسماء غير معروفة.

## 11.4 لو شاشة جديدة

ابدأ بحدود واضحة: route، عناصر أساسية، نموذج، قائمة، ودورة حياة بيانات. استخدم `ScreenPage` إذا يناسب الشاشات العامة، أو منسق المجال إذا هي مستند له بنود. ما تستخدمش وراثة مجال غير مرتبط فقط للحصول على دالة واحدة.

استخرج مكونًا لما تظهر مسؤولية واضحة: اختيار حساب في نافذة، انتظار مزود جدول، بنود مستند، أو نوافذ طباعة. ما تقسّمش لأجل عدد أسطر فقط، ولا تحتفظ بكلاس يعرف كل شيء لأن أسماء دواله قصيرة.

## 11.5 إعادة اختبار مناسبة

تغيير نص أو توثيق لا يحتاج تشغيل Regression ثماني ساعات. تغيير اختيار الصنف المشترك قد يؤثر على أكثر من نوع مستند، فيحتاج اختبارات تمثلهم. تغيير قواعد ملكية التنظيف يحتاج فحوص محلية لحالات الغموض والفشل، وقد يحتاج تحققًا حيًا محدودًا.

بعد تغييرات واسعة: محلي، ثم مسارات حية متأثرة، ثم مجموعات تشغيل أعلى حسب خطة التحقق. لا تعتمد على فحص source أو compile فقط لتعلن نجاح السلوك الحي.

## 11.6 مراجعة الكود كمدير أوتوميشن

اسأل: هل الحالة تقيس هدفًا واحدًا مفهومًا؟ هل تعتمد على بياناتها؟ هل الاسم واضح؟ هل الانتظار له شرط؟ هل الاستثناء يخفي خطأ؟ هل retries ممكن تكرر حفظًا ناجحًا؟ هل الصور والرسائل كافية؟ هل cleanup آمن لو الرد ضاع؟ هل الاختبار يختار العميل/الصنف الصحيح بالهوية لا مجرد أول صف؟

وفي XML اسأل: هل الاختبار مفعّل فعلًا؟ هل include يطابق اسمه؟ هل تكررت الحالة من مسارين؟ هل التنفيذ متسلسل كما تحتاج ملكية الصفحة؟ `SuiteDefinitionsTest` يراجع جوانب من ده آليًا.

## 11.7 لا تنقل الحالات عشوائيًا بين المجموعات

حالة قوية قد تكون طويلة فلا تناسب Smoke. حالة بسيطة قد تكون مهمة جدًا لتسجيل الدخول. E2E يهمه الربط بين الخطوات. Regression يجب أن يحوي التغطية الواسعة بدون تكرار aliases قديمة بلا داعٍ. «زود العدد» مش خطة اختبار.

## 11.8 التعامل مع العيوب

لو فيه عيب في الأداة، اثبته بحالة تفشل ثم أصلحه وأعدها. لو الفشل في ERP قبل إعادة التنظيم وبعدها، سجل المقارنة. لا تغير expected عشان الفعلي يعجبك. لو المتوقع نفسه غير مؤكد، ارجع لقاعدة العمل وأكدها.

## 11.9 التوثيق جزء من التغيير

لو أضفت ملفًا جديدًا، حدّث أطلس الملفات أو أعد توليده بالأداة الموجودة في الدليل. لو غيرت اختيار suite، حدّث مرجع التشغيل بعد فحص الأعداد الفعلية. لو أصلحت عيبًا، اذكر النسخة والدليل، ولا تمسح تاريخ الفشل وكأنه لم يحدث.

## 11.10 ما الذي لا نفعله أثناء الصيانة؟

لا نحذف `target` قبل مراجعة سجلات الاسترجاع، ولا نطبع كلمات السر، ولا ننشئ إعدادات محلية ضمن Git، ولا نرسل تقريرًا لمستلمين دون قصد. ولا نعتبر الملف الفارغ ميزة جاهزة؛ `CSVReader` و`ExcelReader` مجرد هياكل فارغة في النسخة الحالية، رغم وجود ملفات Excel فعلية تُقرأ في اختبارات أخرى عبر مكتبات مختلفة.

## تحديث الدليل بعد تغيير الكود

الفصول التعليمية تُراجع يدويًا؛ السكربت يجدد أطلس الملفات وتوقيعات الميثودات ومرجع XML ولا يعيد كتابة الشرح التعليمي. وصف الغرض المختصر في جداول الميثودات يساعدك على قراءة الاسم، لكنه لا يغني عن قراءة جسم الميثود وشروطها عند تعديلها.

من جذر المشروع، استخدم PowerShell:

```powershell
mvn test-compile
mvn '-DincludeScope=test' '-Dmdep.outputFile=target/documentation-classpath.txt' dependency:build-classpath
$guideCp = 'target/test-classes;target/classes;' + (Get-Content target/documentation-classpath.txt -Raw).Trim()
java -cp $guideCp scripts/DocumentationSuiteInventory.java
python scripts/build_learning_guide.py --html
```

أوامر الحصر السابقة لا تشغل TestNG أو ERP. إذا افتقد Python مكتبة Markdown اللازمة لنسخة HTML فقط، ثبّتها داخل المخرجات المحلية: `python -m pip install --target target/documentation-tools Markdown`. يمكن إنشاء ملفات Markdown دون هذه المكتبة باستبعاد `--html`.

بعدها راجع `DOCUMENTATION_CHECK.json`، وتأكد أن قائمة أخطاء الروابط فارغة، وافتح HTML لمراجعة الشكل. أعداد الاختبارات يجب تجديدها أيضًا داخل فصول الشرح التي تذكرها؛ السكربت لا يغير نص تلك الفصول تلقائيًا. لا تستبدل نتائج تشغيل سابقة بأرقام حصر جديدة؛ الحصر يختار دوال، والتنفيذ قد يكرر الدالة ببيانات مختلفة.

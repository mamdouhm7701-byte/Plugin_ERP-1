# ملخص الفشل ومتابعة الإصلاح

هذا الملف يشرح أين تقرأ سبب التوقف وكيف تتابع العيب حتى إعادة الاختبار.

بعد تشغيل TestNG بالمستمع المعتاد، افتح `target/failure-review/summary.html`.
الملخص مستقل عن تفعيل البريد أو فتح Allure، ولا يغير نجاح أو فشل أي حالة.
يعرض الحالات الفاشلة والمتوقفة والمتخطاة، والقاعدة المعروفة عند وجود تطابق دقيق،
وموضع التوقف، ومرات فشل الحالة في التشغيلات المسجلة، ودليل النتيجة.

كل تشغيل يحتفظ بنسخته داخل `target/failure-review/runs`، مع نسخة من نتيجة الحالة
ومرفقاتها. المرفقات قد تحتوي بيانات بيئة الاختبار؛ هذه ملفات محلية خاصة لا ترفع إلى Git.
تحذف معاملات الإدخال وروابط الجلسة من نسخة النتيجة المخصصة للمراجعة.
الخطأ الفني الأصلي يبقى في Allure؛ الشرح العربي لا يستبدله ولا يخمن سبب انتهاء الانتظار.

## متى نقول إن الفشل تكرر؟

العدد هو مرات فشل نفس الحالة ومعاملاتها ونطاق إعداداتها المسجل، وليس عدد العيوب
ولا إثبات أن السبب نفسه تكرر. تجاهل الحالة لا يمسح فشلها السابق ولا يثبت الإصلاح.
تسجيل الملخص مرتين لنفس الرن لا يزيد العداد. يبدأ التاريخ من أول تشغيل يستخدم هذا التحديث؛
لا يدعي استيراد الرنات القديمة. حذف `target/failure-review` يمسح هذا التاريخ.
الملخص يعتمد نتائج Allure المحفوظة، ويعرض أخطاء التجهيز والتنظيف المسجلة في حاويات
Allure حتى إن لم تبدأ أي حالة. غياب نتيجة أو حاوية من الأصل لا يعد نجاحًا.
الـCI والمخرجات المخصصة تضع الملخص بجانب مجلد نتائجها، كي لا تخلط تاريخها بالتشغيل الحي.

## تصنيف نتائج التشغيل

أعلى الملخص تظهر أعداد «عيب تطبيق»، «عيب اختبار»، «مشكلة بيئة»، «حالة لم تُنفذ»،
و«يحتاج مراجعة»، بجانب عدد الناجح. كل حالة تعرض تصنيفها وسبب التصنيف ودليلها.
الأعداد تشمل أخطاء التجهيز والتنظيف المسجلة، لذلك لا تجمعها مع عدد الحالات الفاشلة مرة أخرى.

- عيب تطبيق: تطابق دقيق مع سجل عيب مؤكد (`confirmed: true` و`kind: APPLICATION_DEFECT`).
- عيب اختبار: دليل تنفيذ واضح مثل محدد عنصر غير صالح، أو فشل تحميل الكود، أو خطأ قيمة خالية في كود الاختبار.
- مشكلة بيئة: خطأ اتصال واضح أو تعذر بدء جلسة المتصفح بسبب بيئة التشغيل.
- حالة لم تُنفذ: تخطٍ؛ حتى لو اسم الحالة مرتبط بعيب قديم.
- يحتاج مراجعة: فشل مقارنة أو انتظار أو ضغط لا يحسم مصدر المشكلة وحده.

النجاح لا يظل مصنفًا كعيب بسبب تاريخه السابق. التصنيف لا يغير نتيجة TestNG أو يغلق التذاكر.
السجل يدعم أيضًا `TEST_DEFECT` و`ENVIRONMENT` للأسباب التي تأكدت بالمراجعة.
وجود معرف داخلي أو كلمة KNOWN_BUG وحدهما لا يكفي لتأكيد عيب تطبيق.

## خطوات متابعة العيب

السجل القابل للتعديل هو `src/main/resources/issue-register.json`.
المعرفات مثل REST-ROUNDING-001 داخلية، وليست تذاكر GitHub منشأة بالفعل.

1. راجع الدليل وأكد القاعدة. اربط العيب بالطريقة وبصمة رسالة محددة، لا باسم الكلاس فقط.
2. ضع رابط التذكرة الحقيقي في `ticket` عند توفره. لا تضع رقمًا وهميًا.
3. بعد تنفيذ الإصلاح، اجعل `state` يساوي `FIX_READY` وسجل الإصدار أو commit في `fixedIn`.
4. شغل الحالة بنفس النشاط والضريبة والخصم والجرد والتننت. النجاح في إعداد مختلف لا يؤكد الإصلاح.
5. النجاح بعد الفشل يظهر «نجح إعادة الاختبار؛ يحتاج تأكيد الإغلاق»؛ لا يغلق السجل تلقائيًا.
6. راجع النتيجة ثم سجل معرف الرن في `verifiedIn` واجعل `state` يساوي `VERIFIED`.
7. عند تكرار العيب بعد الإصلاح اجعله `REOPENED` وأرفق دليل الرن الجديد بالتذكرة.

السجلات ذات `failureContains` الفارغة للمتابعة اليدوية فقط؛ لا تربط أي فشل تلقائيًا.
لا تغير توقّع التست ولا تعطله لإخفاء عيب معروف.

## ضوضاء Allure

الفلتر يستهدف رسائل دورة حياة الخطوة المعروفة فقط حين لا توجد حالة أو خطوة نشطة.
أخطاء Allure داخل الحالة أو الـfixture المسجل تظل ظاهرة. ولو TestNG ينفذ حالة لكن
سياق Allure مفقود، تبقى رسائل الخطأ ظاهرة لكشف خلل ربط التقارير. لا يتم خفض كل أخطاء Allure
إلى تحذيرات أو إخفاء أخطاء التقرير الأخرى.

# تغطية نقاط البيع وفاتورة المطعم

لكل شاشة POM وكلاس اختبارات مستقلان عن فاتورة المبيعات العادية. الأدوات المشتركة في `SpecialSalesPage` تخص عناصر الكاشير فقط.

| الشاشة | المسار | API الحفظ | عدد الحالات المكتوبة |
|---|---|---|---|
| نقاط البيع | `point-of-sale` | `ItemTransactions-PointOfSales` | 15 |
| المطعم | `restaurant-menu` | `ItemTransactions-RestaurantSales` | 15 |

كل حالة موصوفة بالعربية في `@Story` و`@Description`، مع إرفاق بيانات الشاشة والطلبات وأدلة الفشل في Allure.

## قواعد العمل المؤكدة

- فاتورة نقاط البيع الآجلة تزيد مديونية العميل المسجل فور الحفظ بقيمة الصافي غير المدفوع.
- حفظ طلب المطعم أو تعليقه يخصم المخزون فورًا؛ التعليق يبقي الطلب مفتوحًا دون سداد، ويسمح بإضافة بنود.
- دفع الطلب المعلق لا يخصم نفس الكمية مرة ثانية. الإضافة تخصم الزيادة فقط.
- إلغاء فاتورة المطعم يعيد المخزون ويلغي أثر الدفع.
- تعليق سلة نقاط البيع الموجود في الواجهة محلي؛ لا يعادل تعليق المطعم المحفوظ في الخادم.

## الحالات

**نقاط البيع:** الإعدادات المملوكة والقناة، إضافة الباركود، أزرار الكمية، الكمية الكسرية، حذف بند، تعدد الأصناف، تبديل نقدي/آجل، حفظ آجل ورصيد العميل، حفظ نقدي بطريقة دفع مملوكة، تعليق السلة واسترجاعها، تعديل فاتورة محفوظة وخصم فرق الكمية فقط، حذف الفاتورة واستعادة المخزون، رفض تأكيد الحذف، طباعة إيصال محفوظ دون إعادة حفظ، وحفظ وطباعة فاتورة جديدة مرة واحدة.

**المطعم:** الإعدادات والقناة، إضافة من الكتالوج، أزرار الكمية، حذف بند، خارجية/توصيل، تعليق داخلي بطاولة مملوكة وخصم المخزون، فتح المعلق وحفظ بنوده، استمرار الملاحظات بعد الفتح، إضافة إلى المعلق وحساب الفرق والإجمالي، دفع المعلق دون تكرار الخصم، حفظ طلب خارجي مدفوع، الكمية الكسرية، حذف طلب مدفوع، طباعة إيصال محفوظ، وحفظ وطباعة طلب جديد.

اختبارات الطباعة ترصد نافذة الإيصال الحقيقية وتستدعي طباعة المتصفح الأصلية، وتتحقق من اسم الصنف ورقم الفاتورة وثبات عدد مرات الحفظ والمخزون. لا تدعي إنشاء أو فحص ملف PDF مُصدّر.

## دورة حياة البيانات

- `SpecialSalesTestData` ينشئ بياناته تلقائيًا داخل التننت والفرع الحاليين، دون معرفات تننت ثابتة أو الاعتماد على سجلات العمل الموجودة.
- التصنيفات والوحدات والمخازن وحسابات المخازن ثابتة ومشتركة داخل مجموعة الصفحة.
- لكل حالة أصناف وعملاء وطرق دفع وحسابات مستقلة؛ لا تعتمد نتيجة حالة على مخزون أو رصيد حالة أخرى.
- `@AfterMethod(alwaysRun=true)` يسجل محاولات الحفظ والنتائج ويجمع الأدلة، ويرجع إعدادات الفرع المؤقتة ويغلق النوافذ الإضافية. إرجاع الإعدادات بعد كل حالة ضروري لمنع تسرب العميل/المخزن الافتراضيين إلى الحالة التالية أو التشغيل العادي.
- `@AfterClass(alwaysRun=true)` يحذف السجلات المملوكة فقط بترتيب عكسي للاعتماديات، حتى مع فشل حالات. لا يوجد `DeleteAll`.
- التحقق من الملكية يسبق الحذف. تغيير إعداد خارجي أثناء التشغيل يمنع الكتابة فوقه ويحفظ سجل الاسترجاع والاعتماديات.
- سجلات الاسترجاع: `target/special-sales-fixtures`؛ نوايا ومحاولات الكتابة: `target/special-sales-attempts`. لا يجوز حذف سجل غير فارغ لإخفاء فشل التنظيف. الاسترجاع يكون عبر `SpecialSalesTest.SpecialSalesRecovery` وبلاحقة التشغيل المحددة فقط.

## التشغيل

### الربط بتصنيفات المشروع

شاشتا الكاشير مدمجتان في ملفات التشغيل العامة دون تعديل assertions أو نقل وظائفهما إلى الفاتورة العادية:

| التصنيف | اختيارات الكاشير |
|---|---|
| Smoke | فاتورة نقاط بيع نقدية وطلب مطعم خارجي مدفوع |
| Sanity | نقاط البيع: نقدي وآجل وإلغاء حذف؛ المطعم: خارجي مدفوع وزيادة معلق ودفعه دون تكرار الخصم |
| Regression | كل15 حالة لكل شاشة واختبارات إدارة البيانات السبعة، من special-sales-testng.xml مرة واحدة |
| E2E | 3 رحلات نقاط بيع و4 مطعم من الحالات المحفوظة والمترابطة، موضحة في E2E_COVERAGE_AR.md |

هذه إضافة لتصنيف التشغيل فقط؛ لا تعني إعادة تنفيذ النتائج السابقة. فحص المراجع وXML والتجميع لا يثبت نجاح الحالات على التطبيق. عند اختيار دوال محددة تستمر callbacks الإعداد والأدلة واسترجاع إعدادات الفرع والتنظيف.

شغّل TestNG باستخدام أحد الملفات:

- `src/test/resources/point-of-sale-testng.xml`
- `src/test/resources/restaurant-testng.xml`
- `src/test/resources/special-sales-testng.xml` للشاشتين بالتتابع.

اختبارات دورة البيانات المحلية: `SpecialSalesTest.SpecialSalesCleanupTest`، وعددها 7؛ تتحقق من المشاركة والعزل وترتيب الحذف ورفض تغير الملكية واسترجاع التشغيل المنقطع وملكية الطاولات.

## نتائج التحقق

تم تنفيذ **30 حالة واجهة مختلفة: 27 ناجحة، و3 فاشلة بسبب عيوب التطبيق التالية**، إضافة إلى **7 اختبارات محلية ناجحة لإدارة البيانات**. التجميع يعتمد آخر نتيجة لكل اسم حالة كامل (الكلاس + الدالة)، وليس عدد التشغيلات المكررة.

نتائج الجولات محفوظة بشكل مستقل عن تشغيلات المشروع الأخرى:

- `target/special-sales-verification`: التغطية الأساسية.
- `target/special-sales-final-check`: تأكيد العيوب وإعادة التحقق من الحالات المتأثرة.
- `target/special-sales-native-actions`: نجاح حفظ وطباعة الشاشتين وحذف طلب المطعم.
- `target/special-sales-receipt-final`: نجاح طباعة إيصال مطعم محفوظ من القائمة بعد إصلاح التعامل مع الفلتر المختار بالفعل.
- `target/special-sales-latest-results.json`: فهرس آخر نتيجة وأدلتها لكل حالة من الثلاثين.
- `target/special-sales-local-final2/testng-results.xml`: نجاح اختبارات إدارة البيانات السبعة.

نجح تجميع المشروع (`test-compile`) وتنسيق ملفات Java الجديدة باستخدام Google Java Format بنمط AOSP. التغييرات الخاصة بهذه المهمة في ملفات POM واختبارات وسويتات جديدة؛ لم تُعدَّل صفحات الفاتورة العادية أو الاختبارات السابقة ضمن هذه المهمة. لم يُنفذ رن شامل لباقي وحدات المشروع، لذلك نجاح التجميع لا يعادل إثباتًا لتغطية رجعية كاملة لها.

اكتمل تنظيف كل الجولات؛ مجلدا سجلات الاسترجاع ومحاولات الكتابة لا يحتويان سجلات معلقة غير فارغة وقت إنهاء المهمة.

عيوب تطبيق مثبتة حاليًا:

1. نقاط البيع الآجلة: فاتورة صافيها 100 محفوظة على عميل مسجل مستقل، خصمت وحدة مخزون، لكن رصيد العميل ظل صفرًا. هذا يخالف تأكيد العمل بأن الدين يظهر فور الحفظ.
2. المطعم: الملاحظات لا تستمر عند إعادة فتح الطلب المعلق.
3. المطعم: بعد إضافة صنف إلى طلب معلق، مجموع سطري البنود 200 بينما إجمالي رأس الشاشة يبقى 100. الاختبار يتوقف عند عدم الاتساق قبل دفع مبلغ خاطئ.

هذه العيوب تظل تأكيدات فاشلة مع الأدلة؛ لم تُغيّر الاختبارات لقبول السلوك المخالف. إصلاح كود التطبيق نفسه غير متاح في مستودع الأتمتة الحالي.

التغطية الحالية لا تدعي حصر جميع سيناريوهات الضرائب والعروض والإضافات والصلاحيات والتزامن والعمل دون اتصال أو التقارير المحاسبية. نتائج التحقق تخص الحالات المنفذة والبيئة الحالية.
